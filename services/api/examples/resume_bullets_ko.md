# Resume Experience Writing & Comparative Evaluation Prompt

## 1. 목적 (Objective)

제공된 경력, 프로젝트 자료 및 Job Description(JD)을 분석하여 지원자의 담당 역할, 기술적 기여, 문제 해결 능력과 검증 가능한 성과를 효과적으로 전달하는 이력서 Bullet Points를 작성한다.

단순한 업무 요약이나 기술 키워드 나열이 아니라, 실제로 무엇을 설계하고 구현했으며 어떤 결과를 검증했는지 명확하게 보여준다.

**핵심 운영 원칙**

1. 5가지 Writing Structure로 각각 완성된 이력서 초안을 작성한다.
2. 모든 초안을 제시한 후 각 방식의 장단점과 직무 적합성을 비교한다.
3. AI는 가장 적합한 방식과 차선책을 추천하고 구체적인 근거를 설명한다.
4. 사용자는 모든 초안을 읽고 최종 방식을 선택한다.
5. 사용자가 원하면 서로 다른 방식의 장점을 결합한 Hybrid Version을 작성한다.
6. 사실 정확성, 기술적 기여, 직무 적합성, 검증 가능한 성과, 가독성을 우선한다.

---

## 2. 이력서 작성 방식 (Writing Structures)

기본적으로 경력 또는 프로젝트 하나당 3개의 Bullet Points를 작성한다.

다음 5가지 방식을 모두 작성하며, 각 방식의 구조적 특징을 유지한다.

### 방식 1. Role → Contribution → Impact

1. **Role & Scope:** 수행한 프로젝트, 담당 업무, 책임 범위
2. **Technical Contribution:** 직접 설계, 개발, 구현 또는 개선한 기술적 작업
3. **Impact & Evidence:** 정량적 성과, 개선 효과 또는 검증 결과

**적합한 상황:** 역할과 기술적 기여, 성과가 균형 있게 존재하는 경험

### 방식 2. Technology-Based

1. **Technical Capability A:** 핵심 기술 A와 실제 구현 내용
2. **Technical Capability B:** 핵심 기술 B와 실제 구현 내용
3. **Technical Capability C:** 핵심 기술 C와 실제 구현 내용 및 성과

**적합한 상황:** 서로 구분되는 기술적 역량을 여러 개 보유한 경험

각 Bullet은 단순 기술명이 아니라 해당 기술을 사용해 실제로 수행한 작업을 설명한다. 기술이 세 종류보다 적다면 존재하지 않는 기술을 추가하지 않고 실제 작업 단위로 구성한다.

### 방식 3. Impact-First

1. **Key Achievement:** 가장 설득력 있는 정량적 또는 정성적 성과
2. **Implementation:** 성과와 관련된 핵심 구현 및 개선 방법
3. **Role & Scope:** 본인의 역할과 프로젝트 범위

**적합한 상황:** 강한 정량적 성과와 명확한 검증 근거가 존재하는 경험

### 방식 4. Problem → Solution → Result

1. **Problem & Objective:** 해결해야 했던 기술적 또는 비즈니스 문제
2. **Solution & Engineering Approach:** 문제 해결을 위해 설계하고 구현한 방법
3. **Result & Validation:** 해결 결과와 객관적 검증 근거

**적합한 상황:** 기술적 문제 해결 과정과 Engineering Decision이 중요한 경험

### 방식 5. Engineering Lifecycle

1. **Design:** 요구사항, Architecture, Workflow 및 Evaluation 설계
2. **Implementation:** 핵심 시스템, 기능 및 Pipeline 구현
3. **Evaluation & Operations:** 성능 평가, 검증, 개선 또는 실제 운영

**적합한 상황:** 설계부터 구현과 평가까지 여러 개발 단계를 직접 수행한 경험

실제로 수행하지 않은 단계는 만들어내지 않는다. 배포하거나 운영한 경험이 없다면 Evaluation 중심으로 작성하며 Production 운영을 암시하지 않는다.

## 3. 공통 작성 규칙 (Universal Writing Rules)

모든 방식과 Hybrid Version에 동일하게 적용한다.

### 3.1. 길이와 구조 (Length & Structure)

- 경력 또는 프로젝트 하나당 기본 3개 Bullet Points를 작성한다.
- 각 Bullet은 최종 PDF에서 **1~2줄**을 목표로 한다.
- 글자 수보다 핵심 정보, 기술적 정확성 및 가독성을 우선한다.
- 3줄 이상 길어질 가능성이 높다면 중요도가 낮은 표현이나 기술명을 제거한다.
- 각 Bullet은 독립적으로 읽어도 의미가 명확해야 한다.
- 동일한 역할, 기술, 작업, 성과를 여러 Bullet에서 불필요하게 반복하지 않는다.
- 실제 기술적 기여가 많다면 중요한 정보를 삭제하기보다 Bullet 수 조정이나 재구성을 검토한다.
- 회사 소개, 일반적인 배경 설명, 추상적인 업무 설명은 최소화한다.
- PDF의 실제 줄바꿈은 서체와 레이아웃에 따라 달라지므로, 최종 문서가 있다면 실제 렌더링 결과로 검증한다.

### 3.2. 기술적 기여 (Technical Contribution)

기본 서술 요소는 다음과 같다.

**Action + Technical Contribution + Method/Context + Result**

단, 모든 Bullet에 네 요소를 기계적으로 포함하지 않는다.

- 본인이 직접 수행한 작업을 우선한다.
- 팀 전체의 업무와 개인의 기여를 구분한다.
- 사용한 기술 자체보다 해당 기술로 무엇을 구현했는지 설명한다.
- 설계, 개발, 구현, 자동화, 최적화, 평가, 검증 등 실제 수행한 행동을 명확히 한다.
- 중요한 Engineering Decision, Architecture, Algorithm 및 Trade-off는 가능한 범위에서 드러낸다.
- 기술명을 많이 포함하는 것보다 핵심 구현의 구체성을 우선한다.
- 직접 수행하지 않은 작업을 본인의 기여로 표현하지 않는다.

### 3.3. 성과 및 정량화 (Impact & Quantification)

- 검증 가능한 정량적 성과를 우선 활용한다.
- 정확도, 성능 개선율, 처리량, 응답시간, 오류율, 시간 절감, 데이터 규모, 사용자 수, 평가 결과 등을 사용할 수 있다.
- 수치는 제공된 원본 자료에서 확인한 값만 사용한다.
- Baseline, 평가 조건, 데이터셋, 표본 크기와 결과 적용 범위를 필요한 수준에서 명확히 한다.
- 단순한 처리 규모를 성능 향상이나 효율 개선으로 표현하지 않는다.
- 실험 결과, 내부 평가, 외부 PoC 검수, 실제 Production 운영 성과를 구분한다.
- 기술적 변경과 성과 사이에 인과관계가 검증되지 않았다면 단정하지 않는다.
- 정량적 근거가 없다면 검증 가능한 정성적 결과를 사용한다.
- 성과가 없는 경우 임의로 만들어내지 않는다.
- 같은 수치를 여러 Bullet에 반복하는 대신 서로 다른 기여나 결과를 전달한다.

### 3.4. 기술 용어 및 전문성 (Technical Accuracy)

- 업계 표준 Technical Terminology를 사용한다.
- Architecture, Framework, Library, Algorithm, Methodology, Evaluation Metric 등을 정확하게 구분한다.
- AI Agent, Multi-Agent, Agentic RAG, Tool Routing, MCP, A2A, LLM Evaluation, Benchmark, Human-in-the-Loop 등의 용어는 실제 구현에 부합할 때만 사용한다.
- 단순 LLM API 호출을 Agent 개발로 과장하지 않는다.
- 단순 Prompt 사용과 체계적인 Prompt Optimization을 구분한다.
- 단순 테스트와 Benchmark 구축, Evaluation Framework 설계를 구분한다.
- 실제 구현하지 않은 기술을 JD에 맞추기 위해 삽입하지 않는다.
- 기술 스택을 나열하기보다 구현 내용과 연결하여 설명한다.
- 기술적 전문성을 유지하면서 채용 담당자도 핵심 기여를 이해할 수 있도록 작성한다.

### 3.5. 한국어 이력서 문체 및 문법 (Korean Resume Writing Style)

**기본 원칙: 간결하고 자연스러운 한국어 명사형 종결을 사용한다.**

#### A. 명사형 종결 (Nominal Ending)

- 기본적으로 '설계', '개발', '구현', '구축', '분석', '자동화', '최적화', '검증', '개선', '선정', '달성' 등 명사형으로 문장을 끝낸다.
- '개발했습니다', '선정했습니다', '수행했습니다' 같은 서술형 종결은 특별한 이유가 없다면 사용하지 않는다.
- 마지막에 핵심 행동이나 성과가 드러나도록 작성한다.
- 동일한 경력 내 Bullet의 문체를 일관되게 유지한다.

예시:

변경 전:
- 평가 결과를 분석하여 언어별 최적안을 선정했습니다.

변경 후:
- 평가 결과 분석을 통한 언어별 최적안 선정

변경 전:
- LangChain을 활용하여 Fluency Agent를 개발했습니다.

변경 후:
- LangChain 기반 Fluency Agent 개발

변경 전:
- 외부 전문가 검수에서 97.5%의 무수정 통과율을 달성했습니다.

변경 후:
- 외부 전문가 검수에서 97.5% 무수정 통과율 달성

#### B. 조사 최소화 (Particle Reduction)

- 문맥상 의미가 명확하다면 '을/를', '은/는', '이/가', '의' 등의 조사를 생략할 수 있다.
- 모든 조사를 기계적으로 제거하지 않는다.
- 조사 생략으로 주체, 대상, 기술적 관계 또는 인과관계가 모호해진다면 유지한다.
- 문장 압축보다 자연스러운 한국어 문법과 정확한 의미 전달을 우선한다.

예시:

변경 전:
- LLM의 번역 품질을 평가하기 위한 Benchmark를 구축

변경 후:
- LLM 번역 품질 평가 Benchmark 구축

변경 전:
- 전문가의 검수 결과를 기반으로 프롬프트를 최적화

변경 후:
- 전문가 검수 결과 기반 프롬프트 최적화

#### C. 행동 중심 표현 (Action-Oriented Writing)

- '참여', '경험', '관여', '지원'처럼 기여 수준이 모호한 표현을 불필요하게 사용하지 않는다.
- 실제 수행한 작업에 따라 '설계', '개발', '구현', '자동화', '평가', '검증', '최적화' 등을 선택한다.
- 지원 업무만 수행했다면 직접 개발하거나 주도한 것처럼 과장하지 않는다.
- '프로젝트에 참여하여 다양한 경험을 쌓음'처럼 실질적인 기여가 없는 문장을 피한다.

#### D. 불필요한 표현 제거 (Conciseness)

- 불필요한 주어, 수식어와 연결어를 제거한다.
- '이를 통해', '해당 프로젝트에서', '성공적으로', '효율적으로', '다양한', '혁신적인' 등 의미를 추가하지 않는 표현을 최소화한다.
- 한 문장에 과도하게 많은 기술명과 작업을 나열하지 않는다.
- 쉼표와 접속사를 남용하지 않는다.
- '기반', '활용', '통한' 등을 반복하여 기계적인 문장을 만들지 않는다.
- 기술적 의미가 달라지는 경우에는 필요한 연결어를 유지한다.

#### E. 의미 중복 제거 (Semantic Redundancy)

**의미가 동일하거나 유사한 단어를 불필요하게 나열하지 않는다. 다만 기술적으로 구분되는 중요한 작업은 유지한다.**

다음 표현은 중복 가능성을 검토한다.

- 입력 및 갱신
- 수집 및 크롤링
- 검증 및 확인
- 개선 및 최적화
- 자동화 시스템 개발 및 업무 자동화
- 평가 및 검증을 통한 평가 결과 검증

위 표현들이 항상 동의어라는 뜻은 아니다. 실제 작업 범위를 확인한 뒤 압축 여부를 결정한다.

**예시 1. 입력과 갱신**

변경 전:
- OpenPyXL 기반 Excel 데이터 입력 및 갱신 자동화

변경 후:
- OpenPyXL 기반 Excel 데이터 처리 자동화

단, 신규 데이터 입력과 기존 데이터 업데이트가 기술적으로 중요한 경우에는 구분하여 유지한다.

**예시 2. 수집과 크롤링**

변경 전:
- Selenium 기반 웹 데이터 수집 및 크롤링 자동화

변경 후:
- Selenium 기반 웹 크롤링 자동화

**예시 3. 검증과 확인**

변경 전:
- API 응답 데이터 검증 및 오류 여부 확인

변경 후:
- API 응답 데이터 유효성 검증

**의미 중복 제거 기준**

1. 두 표현이 실제로 다른 작업을 나타내는가?
2. 그 차이가 이력서에서 중요한가?
3. 상위 개념으로 통합해도 의미가 유지되는가?
4. 압축으로 인해 기술적 기여나 구현 복잡성이 사라지는가?
5. 더 짧은 표현이면서도 구체성을 유지할 수 있는가?

단순 표현 중복과 실제 Functional Scope의 차이를 구분한다.

데이터 수집과 정제, 모델 학습과 평가, 시스템 설계와 구현, 모니터링과 장애 대응처럼 구별되는 작업은 무조건 통합하지 않는다.

#### F. 자연스러운 문법 및 병렬성 (Naturalness & Parallelism)

- 명사형 종결을 적용하더라도 부자연스러운 명사 나열을 피한다.
- 필요한 조사와 연결어는 유지한다.
- 수식 관계와 작업 간 선후관계가 명확해야 한다.
- 여러 기술과 작업을 나열할 때 문법적 병렬성을 유지한다.
- 직역투, 불필요한 영어 혼용, 중복되는 표현을 최소화한다.
- 동일 경력 내 문장 구조와 표현 수준을 일관되게 유지한다.
- 간결성보다 기술적 정확성과 자연스러운 문장을 우선한다.

### 3.6. Job Description Alignment

- JD가 제공되면 주요 업무, 필수 역량, 우대 역량을 분석한다.
- 지원자의 경험 중 해당 요구사항과 직접 연결되는 항목을 우선한다.
- ATS에서 인식 가능한 표준 기술 키워드를 자연스럽게 포함한다.
- 키워드 일치보다 실제 구현과 기여의 증거를 우선한다.
- JD에 없는 기술이라도 지원자의 강점을 입증한다면 유지할 수 있다.
- JD와 일치하지 않는 경험을 억지로 연결하지 않는다.
- JD가 없다면 제공된 지원 직무와 경험을 기준으로 평가한다.

### 3.7. 사실 검증 (Evidence Integrity)

- 제공된 원본 자료에서 확인되는 사실만 사용한다.
- 기간, 역할, 기술, 수치, 성과를 임의로 변경하지 않는다.
- 직접 수행한 작업과 팀 전체 성과를 구분한다.
- 설계, 구현, 실험, PoC, 배포, Production 운영을 정확하게 구분한다.
- 평가 결과는 실제 평가 범위와 조건에 맞게 기술한다.
- 기술적 변경과 성과의 인과관계를 근거 없이 단정하지 않는다.
- 확인되지 않은 사실은 별도 검증 필요 항목에 표시한다.
- 근거가 불확실한 수치나 기술을 최종 Bullet에 포함하지 않는다.
- 사실 정확성을 문장의 전문성이나 설득력보다 우선한다.

---

## 4. 작성 방식 비교 및 AI 추천 (Comparative Evaluation)

5가지 초안을 모두 실제로 작성한 다음 비교한다.

### 4.1. 평가 기준

| 평가 기준 | 판단 질문 |
|---|---|
| JD Relevance | 지원 직무의 요구 역량을 잘 전달하는가? |
| Technical Contribution | 개인이 직접 수행한 기술적 기여가 명확한가? |
| Impact & Evidence | 객관적 성과와 검증 근거가 잘 드러나는가? |
| Experience Characteristics | 해당 프로젝트의 실제 특성과 구조가 적합한가? |
| Readability | 제한된 분량에서 핵심 정보를 빠르게 파악할 수 있는가? |
| Coverage & Redundancy | 중요한 정보 누락과 반복을 최소화하는가? |

모든 기준에 기계적으로 동일한 가중치를 적용하지 않는다. 경력의 특성과 JD에 따라 중요도를 조정한다.

### 4.2. AI 추천 원칙

- 완성된 5가지 초안을 비교한 후 추천한다.
- 가장 적합한 방식 하나를 선정한다.
- 실제 Bullet의 내용과 JD를 근거로 구체적인 선정 이유를 설명한다.
- 다른 방식보다 유리한 점뿐 아니라 약점도 설명한다.
- 두 번째로 적합한 방식도 제시한다.
- 여러 방식의 강점을 결합하면 더 나은 결과가 가능한지 판단한다.
- AI의 추천은 최종 확정이 아니며 사용자가 직접 선택한다.

**서로 다른 경력이나 프로젝트에는 다른 Writing Structure를 추천할 수 있다.**

---

## 5. 작업 절차 (Workflow)

### Step 1. Experience Extraction

제공된 자료에서 다음 정보를 추출한다.

- 프로젝트 목적과 문제 상황
- 본인의 역할 및 책임
- Architecture와 기술 스택
- 직접 수행한 구현과 개선
- Engineering Decision
- 평가 방법과 결과
- 검증 가능한 정량적 성과

### Step 2. JD Analysis

- 주요 업무 및 요구 역량 분석
- 필수 및 우대 기술 식별
- 실제 경험과의 연결성 평가
- 우선적으로 강조할 기술과 성과 선정

### Step 3. Content Prioritization

- 가장 중요한 기술적 기여 선정
- 강한 성과와 검증 근거 선정
- 중요도가 낮은 기술과 설명 제거
- 의미가 겹치는 작업 및 표현 통합
- 핵심 정보 손실 여부 확인

### Step 4. Five-Structure Drafting

5가지 방식 모두 완성된 이력서 초안으로 작성한다.

각 방식은 기본 3개 Bullet Points로 구성한다.

방식 이름이나 작성 방향만 설명하고 초안을 생략하지 않는다.

### Step 5. Style Refinement

각 초안을 다음 기준으로 다듬는다.

- 한국어 명사형 종결
- 불필요한 조사 제거
- 의미 중복 제거
- 행동 중심 표현
- 기술적 정확성
- 1~2줄 목표
- 자연스러운 문법과 가독성

### Step 6. Comparative Evaluation

실제 초안을 기준으로 강점, 약점, 직무 적합성 및 강조되는 역량을 비교한다.

### Step 7. AI Recommendation

가장 적합한 방식과 차선책을 추천하고 그 근거를 설명한다.

### Step 8. Verification

- 수치와 사실의 정확성
- 실제 구현 여부
- 개인 기여와 팀 성과의 구분
- 평가 조건 및 범위
- 문체와 의미 중복
- Bullet 간 중복과 정보 누락
- JD 관련성

### Step 9. User Decision

모든 초안을 사용자에게 제시하고 최종 방식을 선택하도록 한다.

필요하다면 사용자가 선호한 Bullet을 조합하여 Hybrid Version을 작성한다.

검증되지 않은 내용은 최종 이력서 초안에 사실처럼 포함하지 않는다.

## 8. 최종 실행 지시 (Final Instructions)

다음 순서로 작업하라.

1. 경력 및 프로젝트 자료와 JD를 분석한다.
2. 개인의 역할, 기술적 기여, 구현 내용, 성과와 검증 근거를 추출한다.
3. **5가지 Writing Structure 모두 각각 3개의 완성형 Bullet Points로 작성한다.**
4. 한국어 이력서에는 명사형 종결을 기본으로 적용한다.
5. 의미가 명확한 경우 불필요한 조사를 생략한다.
6. 의미가 중복되는 표현은 압축하되 중요한 기술적 구분은 유지한다.
7. 기술적 정확성, 사실 관계, 성과 근거, 자연스러운 문법, 분량을 검증한다.
8. 5가지 초안을 모두 사용자에게 제시한다.
9. 작성된 결과를 기준으로 각 방식의 장단점과 JD 적합성을 비교한다.
10. **AI가 가장 적합한 방식을 추천하고 실제 경험과 JD에 기반한 구체적인 이유를 설명한다.**
11. 차선책과 Hybrid Version의 가능성을 제시한다.
12. 사용자가 모든 초안을 직접 검토한 후 최종 방식을 선택하도록 한다.

### 최우선 원칙

**Fact Accuracy → Technical Contribution → JD Relevance → Impact & Evidence → Readability & Conciseness**

- 검증되지 않은 사실이나 성과를 만들어내지 않는다.
- 개인의 기술적 기여를 정확하고 구체적으로 설명한다.
- 지원 직무와 관련성이 높은 경험을 강조한다.
- 정량적 성과와 평가 근거를 활용한다.
- 한국어 이력서에는 자연스러운 명사형 문체를 적용한다.
- 불필요한 조사, 의미 중복, 장황한 설명을 제거한다.
- 문장 압축으로 기술적 정확성이나 정보가 손실되지 않도록 한다.
- 형식을 기계적으로 맞추기 위해 중요한 기여를 누락하지 않는다.
- 모든 작성 방식을 실제 초안으로 보여준 후 추천한다.
- 최종 선택은 사용자에게 맡긴다.

**최종 목적: 지원자의 실제 기술적 기여와 검증 가능한 성과를 가장 정확하고 설득력 있게 전달하면서, 사용자가 5가지 완성된 이력서 초안을 직접 비교하여 최적의 표현을 선택할 수 있도록 지원한다.**
